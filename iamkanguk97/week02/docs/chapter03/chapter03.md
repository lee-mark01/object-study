# 3장: 역할, 책임, 협력

## 0. 2장 돌아보기

- 클래스, 추상 클래스, 인터페이스를 조합해 객체지향 프로그램을 구조화한다.
- 상속을 이용해 다형성을 구현한다.
- 다형성은 **지연 바인딩**(lazy binding), 즉 메시지와 메서드를 실행 시점에 연결하는 방식으로 구현된다.
- 상속은 코드를 재사용하는 가장 널리 알려진 기법이다. 하지만 캡슐화 측면에서는 합성이 더 좋은 방법이다.
- 컴파일 시간 의존성과 실행 시간 의존성은 다를 수 있고, 이 둘이 달라야 유연한 객체지향 프로그램을 만들 수 있다.

2장이 클래스와 상속이라는 **구현 도구**를 보여 줬다면, 3장은 그 도구를 쓰기 전에 무엇을 먼저 고민해야 하는지를 다룬다.

> 객체지향 설계의 핵심은 **협력**을 구성하기 위해 적절한 객체를 찾고, 그 객체에 적절한 책임을 할당하는 과정에서 드러난다.
> 클래스와 상속은 객체들의 책임과 협력이 어느 정도 자리를 잡은 뒤에 사용하는 구현 메커니즘일 뿐이다.

## 1. 협력

영화 예매 시스템에서 예매 요청이 처리되는 흐름은 다음과 같다.

```text
1. Screening.reserve(customer, audienceCount)
   → "상영아, 이 정보로 예매 좀 해 줘."
2. Movie.calculateMovieFee(screening)
   → "Movie야, 이 상영 정보로 요금 좀 계산해 줘."
3. AmountDiscountPolicy.calculateDiscountAmount(screening)
   → "AmountDiscountPolicy야, 이 정보로 할인 금액 좀 계산해 줘."
4. DiscountCondition.isSatisfiedBy(screening)
   → "DiscountCondition아, 이 정보로 할인 조건을 만족하는지 확인해 줘."
...
```

여러 객체가 `영화 예매`라는 기능을 구현하려고 메시지를 주고받으며 상호작용한다. 이것을 **협력**(collaboration)이라고 한다.
객체가 협력에 참여하기 위해 수행하는 로직은 **책임**(responsibility)이다.
그리고 객체들이 협력 안에서 수행하는 책임이 모여 그 객체의 **역할**(role)을 이룬다.

### 메시지 전송

메시지 전송은 객체끼리 협력할 때 쓸 수 있는 **유일한 커뮤니케이션 수단**이다.
객체는 다른 객체의 내부 구현에 직접 접근할 수 없으므로, 요청은 오직 메시지로만 전달할 수 있다.

메시지를 받은 객체는 메서드를 실행해 요청에 응답한다.
이때 메시지를 **어떻게 처리할지는 받은 객체가 스스로 선택**한다.

### 자율적인 객체

> 자율적인 객체가 되려면 **자기가 알고 있는 정보로 직접 행동**해야 한다.

요금을 Screening이 아니라 Movie가 계산하는 이유도 여기에 있다. 요금 계산에 필요한 정보를 가장 잘 아는 객체가 Movie이기 때문이다.

객체를 자율적으로 만드는 가장 기본적인 방법은 내부 구현을 **캡슐화**하는 것이다.

자율적인 객체도 혼자서 모든 일을 처리하지는 않는다. 책임을 수행하다가 필요한 정보를 모르거나 외부의 도움이 필요하면, 적절한 객체에게 메시지를 보내 협력을 요청한다.
메시지를 받은 객체 역시 직접 처리할 수 없는 부분이 있으면 또 다른 객체에게 도움을 요청한다. 협력은 이렇게 객체에서 객체로 이어진다.

정리하면 **객체**는 **상태와 행동을 함께 캡슐화하는 실행 단위**다.

## 2. 책임

협력에 참여하기 위해 객체가 수행하는 행동을 **책임**이라고 한다.

> 책임이란 객체에 의해 정의되는 응집도 있는 행위의 집합으로, 객체가 유지해야 하는 정보와 수행할 수 있는 행동을 개략적으로 서술한 문장이다.

### 하는 것과 아는 것

책임은 크게 **하는 것**(doing)과 **아는 것**(knowing) 두 가지로 나뉜다.

| 구분 | 내용 |
|---|---|
| **하는 것** | 객체를 생성하거나 계산을 수행하는 등 스스로 하는 것 |
| | 다른 객체의 행동을 시작시키는 것 |
| | 다른 객체의 활동을 제어하고 조절하는 것 |
| **아는 것** | 사적인 정보에 관해 아는 것 |
| | 관련된 객체에 관해 아는 것 |
| | 자신이 유도하거나 계산할 수 있는 것에 관해 아는 것 |

영화 예매 시스템에 대입하면 다음과 같다.

| 객체 | 하는 것 | 아는 것 |
|---|---|---|
| Screening | 영화를 예매한다 | 자신이 상영할 영화 |
| Movie | 요금을 계산한다 | 가격, 어떤 할인 정책이 적용됐는지 |

여기서 두 가지 원칙이 나온다.

- 객체는 자신이 맡은 책임을 수행하는 데 **필요한 정보를 알고 있을 책임**이 있다.
- 객체는 자신이 할 수 없는 작업을 **도와줄 객체를 알고 있을 책임**이 있다.

### CRC 카드

**CRC 카드**는 객체의 이름, 책임, 협력 대상을 카드 한 장에 적어 보는 설계 도구다. CRC는 Class(또는 Candidate), Responsibility, Collaborator의 앞 글자를 딴 이름이다.
카드 한 장이 객체 하나를 나타낸다. 맨 위에 객체 이름을 쓰고, 그 아래 왼쪽에는 객체의 책임을, 오른쪽에는 책임을 수행하면서 도움을 받는 협력 객체를 적는다. 아래는 영화 예매 예제를 카드 두 장으로 옮긴 것이다(좌우 칸은 줄로 나눠 표현했다).

```text
[Screening]
  책임: 영화를 예매한다 / 상영할 영화를 안다
  협력: Movie

[Movie]
  책임: 요금을 계산한다 / 가격과 할인 정책을 안다
  협력: DiscountPolicy
```

코드를 짜기 전에 카드를 움직여 보며 "이 책임은 누가 맡는 게 맞나", "누구에게 도움을 요청해야 하나"를 가볍게 따져 볼 수 있다. 클래스보다 협력과 책임을 먼저 생각하라는 3장의 흐름과 같은 맥락의 도구다.

### 책임 할당

자율적인 객체를 만드는 가장 기본적인 방법
-> 책임을 수행하는데 필요한 정보를 가장 잘 알고 있는 전문가에게 그 책임을 할당
-> `INFORMATION EXPERT(정보 전문가) 패턴`

1. "예매해라" 라는 이름의 메시지로 협력을 시작
2. 메시지를 처리할 적절한 객체를 선택
  -> 영화를 예매하는 책임을 어떤 객체에 할당해야 할까?
  -> 영화 예매와 관련된 정보를 가장 많이 알고 있는 객체?
  -> 상영 시간과 기본 요금을 잘 알아야지? Screening 객체가 적당하겠다.
3. "영화예매"를 위해서는 예매 가격을 알아야한다.
  -> Screening은 영화 가격에 대해서는 잘 모른다.
  -> "가격을 계산해야 한다" 라는 새로운 메시지가 필요하고 적절한 객체를 선정해야함.
  -> 가격을 계산하는데 필요한 정보를 가장 많이 알고있는 객체?
  -> 가격과 할인정책이 필요한데? Movie가 제일 잘 알고있음.

객체지향 설계는 협력에 필요한 메시지를 찾고 메시지에 적절한 객체를 선택하는 반복적인 과정을 통해 이루어진다. 그리고 이런 메시지가 메시지를 수신할 객체의 책임을 결정한다.

`메시지 = Public Interface`

### 책임 주도 설계

협력을 설계하기 위해서는 책임에 초점을 맞춰야 한다.
어떤 책임을 선택하느냐가 전체적인 설계의 방향과 흐름을 결정한다.

이처럼 책임을 갖고 책임을 수행할 적절한 객체를 찾아 책임을 할당하는 방식으로
협력을 설계하는 방법을 `책임 주도 설계(RDD)` 라고 한다.

#### 메시지가 객체를 결정한다.

객체에게 책임을 할당하는데 필요한 메시지를 먼저 식별하고
메시지를 처리할 객체를 나중에 선택했다는 것이 중요하다.
=> **객체가 메시지를 선택하는게 아니라 메시지가 객체를 선택하게 하는게 중요.**

- 객체가 최소한의 인터페이스를 가질 수 있게 된다.
- 충분히 추상적인 인터페이스를 가질 수 있게 된다.

인터페이스는 무엇을 하는지는 표현해야 하지만 어떻게 수행하는지를 노출하면 안된다.

#### 행동이 상태를 결정한다.

대부분 개발자들이 실수하는 부분은 객체의 행동이 아니라 상태에 초점을 맞추는 것이다.
이런 방식은 객체의 내부 구현이 객체의 퍼블릭 인터페이스에 노출되도록 만들기 때문에 캡슐화를 저해한다.

이와 같이 객체의 내부 구현에 초점을 맞춘 설계 방법을 `데이터 주도 설계` 라고 한다.

구현에 대한 결정을 뒤로 미루면서 객체의 행위를 고려하기 위해서는
항상 협력이라는 문맥 안에서 객체를 생각해야 한다.

협력 관계 속에서 다른 객체에게 무엇을 제공해야 하고 다른 객체로부터 무엇을
얻어야 하는지를 고민해야만 훌륭한 책임을 수확할 수 있다.

객체의 상태가 아닌 행동이 중요하다.
**객체가 가질 수 있는 상태는 행동을 결정하고 나서야 결정할 수 있다.**
그리고 이 행동이 객체의 책임이다.

## 역할

### 역할과 협력

`역할`: 객체가 어떤 특정한 협력 안에서 수행하는 책임의 집합

- 영화를 예매할 수 있는 적절한 역할이 뭔가?
- 이 역할을 수행할 수 있는 객체가 Screening 이구나! 선택.
