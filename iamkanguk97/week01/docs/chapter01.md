# 1장: 객체, 설계

## 1. 티켓 판매 애플리케이션

소극장이 이벤트를 연다. 추첨으로 뽑힌 관람객에게는 공연을 무료로 볼 수 있는 초대장을 보낸다.
그래서 관람객은 두 종류로 나뉜다.

- **이벤트 당첨 관람객**: 초대장을 티켓으로 바꾼다.
- **당첨되지 않은 관람객**: 현금으로 티켓을 산다.

| 클래스 | 의미 | 가진 것 |
|---|---|---|
| `Invitation` | 초대장 | 초대 일자 |
| `Ticket` | 티켓 | 요금(`fee`) |
| `Bag` | 관람객의 가방 | 초대장, 티켓, 현금 |
| `Audience` | 관람객 | 가방 |
| `TicketOffice` | 매표소 | 현금, 티켓 목록 |
| `TicketSeller` | 판매원 | 매표소 |
| `Theater` | 소극장 | 판매원, `enter` 메서드 |

소극장은 관람객의 가방 안에 초대장이 있는지 확인한다.

- 초대장이 있으면 이벤트 당첨 관람객이므로 가방에 티켓을 넣어 준다.
- 초대장이 없으면 관람객의 현금에서 티켓 요금을 빼고, 매표소에 그 금액을 적립한 뒤 가방에 티켓을 넣는다.

## 2. 무엇이 문제인가

로버트 마틴은 소프트웨어 모듈의 목적을 세 가지로 꼽는다.

1. 실행 중에 **제대로 동작**해야 한다.
2. **변경하기 쉬워야** 한다. 간단한 작업만으로 바꿀 수 있어야 한다.
3. 코드를 읽는 사람과 **의사소통**할 수 있어야 한다. 읽는 사람이 예상한 대로 동작해야 한다.

처음 작성한 코드(step01)는 1번은 만족하지만 2번과 3번을 만족하지 못한다.

### Theater의 enter 메서드

```kt
package study.chapter01.step01

class Theater(
    private val ticketSeller: TicketSeller
) {
    fun enter(audience: Audience) {
        if (audience.bag.hasInvitation()) {
            val ticket = ticketSeller.ticketOffice.getTicket()
            audience.bag.ticket = ticket
        } else {
            val ticket = ticketSeller.ticketOffice.getTicket()
            audience.bag.minusAmount(ticket.fee)
            ticketSeller.ticketOffice.plusAmount(ticket.fee)
            audience.bag.ticket = ticket
        }
    }
}
```

이 코드에는 문제가 세 가지 있다.

**① 예상을 벗어난다 (의사소통 실패)**

관람객과 판매원이 소극장의 통제를 받는 **수동적인 존재**다.
현실에서는 관람객이 자기 가방에서 초대장을 꺼내 판매원에게 건넨다. 그런데 이 코드에서는 소극장이 관람객의 가방을 마음대로 열어 본다.

**② 한 번에 기억해야 할 것이 많다**

`enter` 하나를 이해하려면 다음 사실을 모두 알고 있어야 한다.

- Audience가 Bag을 가지고 있다.
- Bag 안에 현금과 티켓이 들어 있다.
- TicketSeller가 TicketOffice에서 티켓을 판매한다.
- TicketOffice 안에 돈과 티켓이 보관되어 있다.

**③ 변경하기 어렵다 (결합도가 높다)**

Audience나 TicketSeller가 바뀌면 Theater도 함께 바뀌어야 한다.

- 관람객이 가방 없이 지갑만 들고 온다 → `audience.bag`을 쓰는 Theater 코드를 모두 고쳐야 한다.
- 판매원이 매표소 대신 키오스크를 쓴다 → Theater가 `ticketSeller.ticketOffice`에 직접 접근하므로 Theater도 고쳐야 한다.
- 카드 결제가 추가된다 → 결제 로직이 Theater에 있으므로 Theater를 고쳐야 한다.

> **의존성(dependency)**: 어떤 객체가 바뀔 때, 그 객체에 의존하는 다른 객체도 함께 바뀔 수 있다는 사실.
> **결합도(coupling)**: 객체 사이의 의존성이 지나치면 "결합도가 높다"고 한다.
> 결합도가 높을수록 함께 바뀌어야 하는 코드가 많아진다. 그래서 결합도를 낮춰 변경하기 쉬운 설계를 만드는 것이 목표다.

## 3. 설계 개선 과정

문제의 원인은 Theater가 관람객의 가방과 판매원의 매표소에 **직접 접근**한다는 것이다.
그래서 Theater가 Audience와 TicketSeller의 세세한 내부를 모르게 만든다. 관람객은 가방 속 현금과 초대장을 스스로 처리하고, 판매원은 매표소의 티켓과 요금을 스스로 다루게 한다.
즉, 각 객체를 **자율적인 존재**로 바꾸는 것이 목표다.

모든 단계는 같은 패턴을 따른다. **다른 객체의 내부를 뒤지던 코드를, 그 내부를 가진 객체 안으로 옮긴다.**

| 단계 | 패키지 | 변경한 점 | 변경 이유 |
|---|---|---|---|
| 01 | `step01` | 개선 전 설계 | Theater가 모든 객체 내부에 직접 접근 |
| 02 | `step02` | `TicketSeller.sellTo(audience)` 추가, `ticketOffice`를 `private`으로 | Theater가 TicketOffice를 모르게 |
| 03 | `step03` | `Audience.buy(ticket)` 추가, `bag`을 `private`으로 | TicketSeller가 관람객의 가방을 열지 않게 |
| 04 | `step04` | `Bag.payFor(ticket)` 추가, 내부 상태를 `private`으로 | Audience도 가방 속을 뒤지지 않고 Bag이 스스로 처리하게 |
| 05 | `step05` | `TicketOffice.sellTicketTo(audience)` 추가 | TicketSeller도 매표소 속을 뒤지지 않게 (단, 트레이드오프 있음) |

step04까지 개선하면 객체들은 서로 **메시지**만 주고받는다.

```text
Theater      → TicketSeller : "이 관람객에게 팔아 주세요"   sellTo(audience)
TicketSeller → Audience     : "이 티켓을 사 주세요"        buy(ticket)
Audience     → Bag          : "이 티켓값을 치러 줘"        payFor(ticket)
Bag          → Audience     : "이만큼 냈어"               반환값(Long)
```

결과적으로 **각 객체가 자기 자신의 문제를 스스로 해결**하도록 바뀌었다.
개선 전에는 Theater가 Audience와 TicketSeller의 내부 구현까지 알아야 했다. 지금은 내부에 직접 접근하지 않고 메시지로만 요청한다.

## 4. 개선에서 배운 개념

### 캡슐화와 인터페이스

**캡슐화(encapsulation)**: 객체 내부의 세부 사항을 감추는 것. 이 예제에서는 `private`으로 내부 상태를 숨겼다. 예를 들어 TicketOffice에는 이제 TicketSeller만 접근할 수 있다.

- 캡슐화의 목적은 **변경하기 쉬운 객체**를 만드는 것이다.
- 내부 접근을 막으면 객체 사이의 결합도가 낮아지고, 설계를 바꾸기 쉬워진다.

객체를 **인터페이스**(밖에서 보이는 메서드)와 **구현**(메서드 안의 코드)으로 나누고, 인터페이스만 공개한다. 결합도를 낮추기 위한 가장 기본적인 설계 원칙이다.

- Theater는 TicketSeller 안에 TicketOffice가 있다는 사실을 모른다. TicketSeller가 `sellTo` 메시지를 이해하고 응답한다는 것만 안다.
- 그래서 **구현**을 바꾸면 바깥에 영향이 없다. `buy` 안에서 가방 대신 지갑을 쓰도록 바꿔도 TicketSeller는 그대로다.
- 반대로 **인터페이스**를 바꾸면 영향이 간다. `buy`를 `purchase`로 바꾸면 TicketSeller도 고쳐야 한다.
- 그러므로 메서드 이름은 "어떻게"가 아니라 "무엇을 하는지"(책임)를 담아, 쉽게 바뀌지 않게 지어야 한다.

### 메시지와 자율성

객체끼리는 **메시지**로만 상호작용한다.
`audience.buy(ticket)`은 "사라!"라는 명령이 아니라 "이 티켓을 사 주세요"라는 **요청**이다. 보내는 쪽은 무엇을 원하는지만 말한다. 초대장을 쓸지 돈을 낼지, 어떻게 처리할지는 받는 쪽이 스스로 정한다. 이것이 **자율적인 객체**다.

### 응집도와 결합도

**응집도(cohesion)**: 밀접하게 연관된 일만 하고, 연관 없는 일은 다른 객체에 맡기는 객체를 "응집도가 높다"고 한다.

자기 데이터를 스스로 처리하는 자율적인 객체를 만들면 **결합도는 낮아지고 응집도는 높아진다.**

### 절차지향과 객체지향

| 구분 | 절차지향 | 객체지향 |
|---|---|---|
| 배치 | 프로세스(`enter`)와 데이터(Audience, TicketSeller 등)를 **다른 모듈**에 둔다 | 데이터와 프로세스를 **같은 모듈**에 둔다 |
| 이 예제에서는 | step01: Theater가 모든 처리를 맡고, 나머지 클래스는 데이터만 담는다 | step02 이후: 각 클래스가 자기 데이터를 스스로 처리한다 |
| 의존성 | Theater가 TicketSeller, TicketOffice, Audience, Bag 모두에 의존한다 | 캡슐화로 의존성을 적절히 관리해 결합도를 낮춘다 |

### 책임의 이동

절차지향 설계에서는 Theater처럼 한 객체에 **책임이 몰린다.**
Theater에 몰려 있던 책임이 각 객체로 나뉘어 옮겨 가는 것을 **책임의 이동**이라고 한다.

| 객체 | 책임 |
|---|---|
| Theater | 관람객을 입장시킨다 |
| TicketSeller | 티켓을 판매한다 |
| Audience | 티켓을 구매한다 |

> 객체가 **어떤 데이터를 가지느냐**보다 **어떤 책임을 맡기느냐**에 초점을 맞춰야 한다.

설계를 어렵게 만드는 것은 **의존성**이다. 불필요한 의존성을 없애 객체 사이의 결합도를 낮춰야 한다.
다만 협력에 꼭 필요한 의존성까지 억지로 없애면 안 된다. 메시지를 보내려면 상대를 알아야 하기 때문이다.

## 5. 책과 다르게 생각한 점

### `Bag.hold` 대신 `Bag.payFor`

책은 Bag의 메서드를 `hold(ticket)`(보관하다)라고 짓는다. 그런데 실제로 하는 일은 세 가지다.

1. 티켓을 넣는다 → 이름에 드러남
2. 초대장이 없으면 돈을 뺀다 → 이름에 없음
3. 뺀 금액을 반환한다 → 이름에 없음

"보관해 줘"라고 요청했는데 돈이 빠져나가고 금액이 돌아오니, 이름만 보고는 동작을 예상할 수 없다.
상태를 바꾸면서(명령) 값도 돌려주므로(조회) **명령-조회 분리(CQS, Command-Query Separation)** 원칙에도 어긋난다.

그래서 step04에서는 `payFor(ticket)`("이 티켓값을 치르고, 치른 금액을 알려줘")으로 바꿨다. 초대장이 있으면 "0원을 치렀다"로 읽혀서 반환값이 자연스럽다.
다만 이번에는 "티켓을 넣는다"가 이름에 직접 드러나지 않는다. 하는 일을 모두 이름에 담으면 `holdAndPay`처럼 어색해지므로, 이름에는 **가장 중요한 책임 하나**를 담기로 했다.

### `TicketOffice.sellTicketTo`의 트레이드오프

step05에서는 TicketSeller가 하던 판매 일을 TicketOffice 안으로 옮겼다. TicketOffice의 자율성은 높아졌지만, **TicketOffice가 Audience를 알아야 하는 새 의존성**이 생겼다.

```text
step04: Theater → TicketSeller → TicketOffice
                       ↓
                    Audience

step05: Theater → TicketSeller → TicketOffice
                       ↓              ↓
                    Audience  ←───────┘   (새 의존)
```

| 구분 | step04 | step05 |
|---|---|---|
| TicketOffice의 자율성 | 낮다 (판매원이 시키는 대로) | 높다 (스스로 판매) |
| Audience에 의존하는 객체 | TicketSeller | TicketSeller, **TicketOffice** |

자율성을 높이려다 결합도가 높아졌다. 어느 쪽을 택할지는 상황에 따라 다르다.

> 모든 객체를 자율적으로 만드는 것이 항상 정답은 아니다. **설계는 트레이드오프의 산물이다.**

### 의인화

현실의 가방이나 매표소는 스스로 돈을 내거나 티켓을 팔지 않는다. 그런데도 `Bag.payFor`처럼 가방이 스스로 일하게 만드는 것이 자연스러운 이유는 **의인화(anthropomorphism)** 때문이다.
현실에서는 수동적인 사물이라도, 객체지향 세계에서는 스스로 판단하고 행동하는 자율적인 객체가 된다.

> 훌륭한 객체지향 설계란 소프트웨어를 구성하는 모든 객체가 **자율적으로 행동**하는 설계다.
> 다만 위의 트레이드오프처럼, 자율성을 높이는 과정에서도 의존성이 늘어나지 않는지 함께 따져 봐야 한다.

## 6. 객체지향 설계

> 설계란 코드를 배치하는 것이다.

**좋은 설계**란 오늘 요구하는 기능을 온전히 수행하면서, 내일의 변경을 매끄럽게 받아들일 수 있는 설계다.

- 요구사항은 항상 바뀐다.
- 요구사항이 바뀌면 코드를 고쳐야 하고, 코드를 고치면 버그가 생길 가능성이 높아진다.
- 그래서 변경을 쉽게 받아들일 수 있는 설계가 중요하다.

객체들은 기능을 구현하려고 협력하는 과정에서 서로 의존하게 된다.
예를 들어 TicketSeller가 Audience에 메시지를 보내려면 Audience에 대해 알고 있어야 한다. 이 지식이 두 객체를 결합시키고, 이 결합이 의존성을 만든다.

> **훌륭한 객체지향 설계**란 협력하는 객체 사이의 의존성을 적절하게 관리하는 설계다.

데이터와 프로세스를 하나의 덩어리로 모으는 것은 훌륭한 객체지향 설계로 가는 첫걸음이다.

1장은 "객체가 자기 일을 스스로 하게 만들면 무엇이 좋아지는가"를 티켓 판매 예제로 보여 준다.
Theater가 모든 객체의 내부를 뒤지던 절차지향 코드를 캡슐화와 메시지를 통해 단계별로 고치면, 책임이 각 객체로 옮겨 가고 결합도는 낮아진다.
다만 자율성을 높이는 것이 결합도를 높이기도 하므로(step05), 좋은 설계는 정답을 고르는 일이 아니라 **의존성을 적절히 관리하는 트레이드오프의 선택**이다.
