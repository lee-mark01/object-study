
# 오브젝트 3장 - 역할, 책임, 협력

## 전체 내용 요약

객체지향의 핵심은 클래스가 아니라 **협력, 책임, 역할**이다.

협력이 객체의 행동을 정하고 행동이 상태를 정한다. 그래서 메시지를 먼저 찾고, 그 메시지를 처리할 객체에 책임을 맡기는 **책임 주도 설계**로 설계한다.

같은 책임을 다르게 수행하는 객체가 필요해지면 **역할**로 추상화해 바꿔 끼운다.

## 핵심 내용

### 협력

- 객체지향 프로그래밍에서는 제어 흐름이 한 객체에 몰리지 않고 여러 객체에 고르게 나뉜다. 여러 객체가 메시지를 주고받으며 기능을 구현하는 상호작용이 **협력**이다.

- **메시지 전송**은 객체 간 협력의 유일한 소통 수단이다. 메시지를 받은 객체는 자기 **메서드**로 처리하고, 처리 방법은 받은 객체가 전적으로 정한다.

- 자기가 못 하는 일이나 다른 객체의 내부 정보가 필요한 일은 그 객체에 맡긴다. 그러면 자율성이 올라가고 협력이 자연스럽게 생긴다. 자율적인 객체를 만드는 가장 기본적인 방법은 **캡슐화**다.

- **협력이 행동을, 행동이 상태를 정한다.** 협력은 객체를 설계하는 문맥이다.

> 객체들이 각자 맡은 책임을 수행하기 위해 메시지를 주고받으며 상호작용하는 과정이다.

### 책임

- 협력에 참여하기 위해 객체가 수행하는 행동으로, 객체가 정의하는 응집도 있는 행위의 집합이다.

- **하는 것**
    - 스스로 생성 및 계산
    - 다른 객체의 행동 시작
    - 다른 객체의 활동 제어

- **아는 것**
    - 사적인 객체 내부 정보
    - 관련 객체
    - 유도하거나 계산할 수 있는 것

- 예시
    - `Screening`은 영화를 예매한다(하는 것). 상영할 영화를 안다(아는 것).
    - `Movie`는 요금을 계산한다(하는 것). 가격과 할인 정책을 안다(아는 것).

- 책임은 메시지보다 크고 추상적이다. 처음에는 책임 하나였던 것이 메시지 여러 개로 쪼개지거나, 여러 객체가 협력해야 하는 큰 책임으로 자라는 경우가 흔하다.

- 책임을 정리하는 도구로 **CRC 카드**(Candidate, Responsibility, Collaborator)가 있다. 객체에 어떤 책임이 있고 누구와 협력하는지 적는 인덱스 카드다.

### 책임 할당과 책임 주도 설계

- **정보 전문가 패턴(INFORMATION EXPERT)**: 책임을 수행하는 데 필요한 정보를 가장 잘 아는 객체에 그 책임을 맡긴다. 책에는 "정보 전가 패턴"으로 적혀 있지만, 정식 표현은 정보 전문가 패턴이다.

- 협력 → 책임 → 하위 책임을 반복해서 찾는다.
  영화 예매: 예매하라(상영 시간, 기본 요금) → 가격을 계산하라(가격, 할인 정책) → 할인 요금을 계산하라.

- **책임 주도 설계(RDD)**: 시스템의 책임을 파악해 작은 책임으로 나누고, 그 책임을 맡을 객체나 역할을 찾는다. 도움이 필요하면 다시 그 책임을 맡을 객체를 찾는 과정을 반복한다.

  지켜야 할 것은 두 가지다. **메시지가 객체를 결정하고, 행동이 상태를 결정한다.**
  이와 반대로 객체 내부 구현부터 정하는 방식이 **데이터 주도 설계**다.

### 역할

- 특정 협력 안에서 객체가 수행하는 책임의 집합이자, 객체가 맡는 자리다.
  역할에 요구되는 책임을 수행할 수 있는 객체라면 누구든 그 역할을 맡을 수 있다.

- 예) 금액 할인과 비율 할인을 따로 구현하면 공통 할인 로직이 중복된다. `할인`이라는 역할 하나로 묶고, 구체적인 할인 로직을 구현한 여러 할인 종류를 슬롯처럼 바꿔 끼운다.

- 구현 수단은 추상 클래스와 인터페이스다. 추상 클래스는 일부를 구현하고, 인터페이스는 책임 목록만 둔다.

- 처음부터 역할을 만들지 않고, 같은 책임을 다른 방식으로 수행하는 객체가 필요해질 때 도입한다. **애매하면 구체 객체로 시작하고, 확실하면 역할로 시작한다.**

- 배역(역할)과 배우(객체): 로미오 역을 수행할 책임만 있으면 누구라도 로미오가 될 수 있다. 객체는 여러 역할을 가질 수 있지만, 한 협력은 객체의 한 역할만 본다.

- 같은 역할을 수행하고 계약을 지키는 객체들은 서로 대체 가능하며 **다형적**이다.

- 트리그비 린스카우의 **역할 모델링**: 객체들의 협력 패턴을 역할들의 협력 패턴으로 추상화해 유연하고 재사용 가능한 시스템을 얻는다.

## 정리

그렇다면 행위, 책임, 역할은 어떻게 비교할 수 있을까?

**행위 → 책임 → 역할**을 반드시 단계별로 쌓이는 고정된 계층으로 바라보면 안 될 것 같다.

온라인 쇼핑에서 주문 객체가 다음 일을 한다고 가정해 보자.

| 구분 | 주문 예시 | 설명 |
| --- | --- | --- |
| 행위 | 주문 항목의 금액을 합산한다. <br>할인을 적용한다. | 객체가 하는 구체적인 활동 |
| 책임 | 최종 결제 금액을 계산해 알려 준다. | 협력 상대에게 수행해야 할 의무 |
| 역할 | **결제 금액 제공자 역할** | 그 책임을 맡는 객체가 차지하는 자리 |

결제 객체가 주문 객체에 결제 금액을 요청하는 상황이다.

- 주문 객체는 **결제 금액 제공자 역할**을 한다.
- 그 역할에서 **최종 결제 금액을 알려 줄 책임**이 있다.
- 책임을 수행하면서 **합산하고 할인을 적용하는 행위**를 한다.

만일 장바구니 객체도 최종 결제 금액을 알려 줄 책임을 가진다면, 주문 객체 대신 결제 금액 제공자 역할을 맡을 수 있다. 내부 구현은 서로 달라도 된다.

**행위의 집합이 책임**
- 서로 관련된 행위들을 **어떤 책임을 수행하는가**라는 관점에서 묶은 표현이다.

**책임의 집합이 역할**
- 협력에 필요한 책임들을 **어떤 자리가 맡는가**라는 관점에서 묶은 표현이다. 역할에 반드시 여러 책임이 있어야 하는 건 아니다.

**행위는 하는 일, 책임은 해야 할 일, 역할은 그 일을 맡는 자리**라고 이해하면 좋을 것 같다.

**Q2. 처음 클래스를 작성할 때 상태와 행동 중 무엇을 먼저 작성하는 게 좋은가?** (책의 "행동을 결정하고 상태를 결정해야 한다"와 이어지는 질문이다.)

## 내 생각

하나의 객체가 여러 역할을 할 수 있다는 건 보통 많은 책임을 가진다는 뜻이다. 그러면 갓 클래스가 될 수 있으니, 하나의 객체는 한 가지 역할이나 적절한 수의 역할만 수행하는 것이 바람직한 것 같다.
